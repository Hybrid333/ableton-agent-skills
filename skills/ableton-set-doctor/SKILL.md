# Ableton Set Doctor

Diagnosis and repair for Live 11 sets. Tool: [`tools/set_doctor.py`](../../tools/set_doctor.py)
(needs `als_lib.py` next to it, stdlib only).

```bash
cd tools
export PYTHONDONTWRITEBYTECODE=1

python3 set_doctor.py "path/Track.als"                     # one set
python3 set_doctor.py "path/Music"                         # whole folder
python3 set_doctor.py "path" --sample-db "lib/Ableton" --sample-db "lib/Music"
python3 set_doctor.py "path/Track.als" --repair            # -> Track.repaired.als
```

The original is never overwritten.

If the tools run somewhere other than the Windows machine that owns the sets
(WSL, a Linux VM, an agent sandbox with a mounted folder), set
`ALS_HOST_ROOT` to where `Documents/Ableton` is mounted and `ALS_WIN_ROOT` to the
Windows path, so recorded sample paths can be resolved and written back.

---

## The most common cause of "Live says it's corrupt"

**Colliding pointee IDs.** When a set was generated by deep-copying a track
template, all copies carry the same IDs in `AutomationTarget`, `Pointee`,
`ModulationTarget` and `ControllerTargets.*`. Live refuses the set — usually
without a useful error message.

Measured on a real generated set: **9 tracks shared 156 IDs**, the worst one in
9 copies. After remapping 1,248 IDs the set was clean with identical content
(59 clips, 8,718 notes, 10 locators, tempo 125).

The tool checks and repairs this. IDs that an automation envelope's `PointeeId`
points at are **not** touched — they would lose their automation; those are
reported instead.

---

## Second most common cause: transplanted devices

A script that copies instruments from other projects into a set drags their
sample paths and preset references along. In one case that bloated a file from
165 KB to 540 KB with Drum Racks, Simplers and Operator presets from other
contexts.

**Don't repair — roll back.** If a `.bak` or a version without devices exists,
that's the better starting point: remap IDs, leave instruments empty, let the
user load them.

## Lessons from real sets — don't throw these away

**NoteId is only unique per clip, not per document.** Live itself reuses the
same IDs in different clips. A document-wide check raises false alarms on every
real set. Verified on 45 sets.

**Factory presets are not missing files.** References with
`RelativePathType = 5`, with `LivePackName`, with `Core Library` in the path, or
a bare filename without a directory are resolved by Live internally.

**The same file is referenced many times** — once per device and clip. So
results are grouped by filename with a usage count.

**IDs like `WarpMarker`, `MultiSamplePart`, `RemoteableTimeSignature`,
`AbletonDefaultPresetRef` are locally scoped** and legitimately repeat. Only the
pointer types above are document-wide unique.

## When a set won't load at all

`als_lib.read_raw()` gives a concrete diagnosis:

- **truncated gzip stream** → writing was interrupted. A crash, a full disk, or
  a cloud-sync client copying during the save (Dropbox, OneDrive and iCloud
  running at the same time is a classic).
- **0 bytes** → never written.
- **starts with `<`** → uncompressed XML, still readable.
- **no `<LiveSet>`** → it's an `.adg` rack, not a set.

Always check for a `.bak` next to it or a `Backup/` folder in the project before
declaring a set lost.

## Reporting back

Don't pass the raw output through:

1. Does the set open? If not: why, and where an intact version is.
2. The three to five findings that affect the sound.
3. What was repaired and where the file is.
4. What the user has to decide.

For folder runs: sets with findings sorted by severity, the rest as a count.
